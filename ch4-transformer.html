Inside the transformer, starting from makemore

If you've built makemore, you already know most of the ingredients: embeddings, a context window, an MLP, a normalisation layer with a learnable gain and bias, and "predict the next thing". This chapter adds just two new ideas: attention (tokens fetching information from each other) and conditioning the normalisation on the keyboard. Each is explained from scratch, with something to click.

2 · The problem attention solves

In makemore, the MLP glued the context together by concatenation: 3 characters × 10 dims became one 30-number input. Each slot had fixed weights: "slot 1 means the character three steps back".

Doing that here would mean concatenating 11,520 tokens × 4096 numbers, which is 47 million inputs into one layer. Worse, the useful connections move. When the ball flies across P1's screen, the token that needs to "know about the ball" in P3's view is a different one every frame. Fixed slots can't follow that.

Attention replaces fixed slots with a lookup by content. Every token can ask "who out there is relevant to me?" and take a weighted average of the answers. The weights are computed fresh on every forward pass.

3 · Attention, worked out by hand

Each token produces three vectors, each via its own learned linear layer (just matrix multiplies, like C or W1 in makemore):

query q: "what am I looking for?"
key k: "what do I contain?" (how I advertise myself)
value v: "what I'll hand over if you pick me"

Then, for one query token:

scorej = q · kj / √d   # dot product = similarity
w = softmax(score)   # same softmax as makemore's logits → probs
out = Σj wj · vj   # weighted average of values
x = x + out   # add it to the token (residual)

That's all of attention. Every token does this at the same time, so in practice it is a few big matrix multiplications. (If you go on to Karpathy's "Let's build GPT", this is exactly its self-attention head.)

In the demo the vectors are hand-made and readable: 4 numbers meaning "ball-ness, car-ness, sky/stadium-ness, clock-ness". In MIRA they are 4096-dimensional and learned, but the arithmetic is identical. The paper shows the trained model really does this: a token on P1's car attends to that same car in the other players' views (Fig. 17).

4 · 11,520 tokens is too many, so split space and time

If every token attended to every other token, each step would compute 11,520 (query tokens) × 11,520 (key tokens) ≈ 133 million scores per layer, and that number grows with the square of the context. MIRA uses two cheaper kinds of attention layers and alternates them:

  • Space layer: a token attends only to the 576 tokens of its own frame, across all 4 players' views. This is how the four views stay consistent: P3's view can "ask" P1's view where the ball is.
  • Time layer: a token attends only to the same cell in earlier frames. This carries motion and memory. It is causal: a frame can never look at a later frame, for the same reason makemore never peeks at the character it is predicting.

5 · Steering with the keyboard: AdaLN

Remember makemore's BatchNorm layer:

hpreact = bngain * (hpreact − mean) / std + bnbias

bngain and bnbias were learned parameters, the same for every input. LayerNorm does the same normalise-then-scale-and-shift, except it normalises each token over its own 4096 features instead of over the batch.

AdaLN ("adaptive LayerNorm") has one twist: the gain and bias are not fixed parameters. A small network computes them from a conditioning vector c, which summarises what the 4 players are pressing and how noisy the input currently is (τ from Ch. 02):

c = emb(keys of P1..P4) + emb(τ)
γ, β = Linear(c)   # "gain" and "bias", per block
x̂ = (1 + γ) · LayerNorm(x) + β

So pressing W doesn't add a token. It changes how every token in every block gets scaled and shifted. That's how a keypress reaches the whole picture.

Two details that matter for multiplayer

① Each player's 9 keys go through their own small embedding, and the four results are concatenated in a fixed order (P1, P2, P3, P4). That order matches the stacking order of the views. The same c is used for every token, so the model has to learn that P1's W moves P1's camera and not the sky in P4's view.

② A player's keys can be replaced by a learned "absent" vector. Then the model must guess what that player does, and that's the autopilot (Ch. 05).

6 · One block, then the whole model

A block is three sub-layers. Each one adds its result to the token instead of replacing it: x = x + f(x). This "residual" trick lets gradients flow through 16 stacked blocks, the deep-network problem makemore part 3 fought with careful initialisation.

7 · Jargon decoder (optional)

The paper lists several extra components. None of them change the ideas above. They make a 5-billion-parameter model train stably and run fast.

Multi-head attention (32 heads)
Run 32 small attention lookups side by side, each with its own q/k/v layers, and concatenate the results. One head might track the ball while another tracks the clock.
GQA: grouped-query attention (32 query heads / 8 key-value heads)
Groups of 4 query heads share one key/value head. Fewer keys and values to store means a smaller cache and faster real-time generation (Ch. 06).
RoPE: rotary position embedding
Attention by itself doesn't know where a token is (makemore's MLP knew from the slot). RoPE rotates q and k by an angle that depends on row, column and time, so the score depends on the relative offset. No weights are tied to a grid size, so the single-player model (9 rows) can be warm-started into the 4-player model (36 rows) with the same weights.
QK-norm, sigmoid gate
Normalise q and k before the dot product, and let a learned 0–1 "valve" scale the attention output. Both stop activations from blowing up, the problem makemore's part 3 diagnosed with histograms.
SwiGLU
The per-token MLP, with a gated activation instead of tanh/ReLU. Same role as makemore's hidden layer.
Register tokens
A few extra learnable tokens that aren't image cells. Attention can use them as scratch space for global information.
KV cache
At generation time, the keys and values of past frames don't change, so they are stored and reused instead of recomputed (Ch. 06).
